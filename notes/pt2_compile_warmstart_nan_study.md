# PT2 compile + warm-start composite NaN — bisect study

**Author:** Gabriel de Miranda (with Claude Opus 4.7)
**Date:** 2026-05-18 → 2026-05-19
**Context:** experiment `4-composite_warmstart`; commits `f928908..111d49f` (outer), `31f0fe3..3593e8d` (sparse-delta-core).

## 0. Executive summary

PT2 train-time compile (`torch.compile`, via nequip's `CompileGraphModel`) reproducibly produces NaN gradients in the compiled backward graph of the **warm-start composite** described in [`m1_warmstart_design.md`](m1_warmstart_design.md). Bisect localised the failure to the **force-backward subgraph** — specifically `autograd.grad(E, positions)` inside `ForceStressOutput` for conservative forces. Energy-only training under the same `compile_mode: compile` runs cleanly for 30 epochs; cuEquivariance, dict aliasing, and Inductor codegen nondeterminism are all innocent.

Production config now uses `compile_mode: eager` with cuEquivariance still active via `nequip.model.modify` + `enable_CuEquivarianceContracter` — verified stable for 30 epochs of joint M0+gate+M1 training on `cameron_plus_bulkpt` (val_forces_mae ≈ 0.13 eV/Å, val_per_atom_energy_mae ≈ 0.018 eV/atom by epoch 27).

## 1. Setup

### 1.1 Model

The warm-start composite (`sparse_delta_core.model.build_warmstart_composite`) is a `SequentialGraphNetwork` of: M0 (small Allegro, `num_layers=2`) → `RenameKey` (move M0's per-atom energy aside) → `EdgeFeaturesToNodeLambda` (per-atom gate) → M1 (larger Allegro, `num_layers=1`) with its `tensor_features_in_field` **aliased** to M0's pre-final TP output `_allegro_pre_final_tp_out` → M1 readout / edgewise reduce / per-type scale-shift → `GatedPerAtomEnergyCompose` (`PER_ATOM_ENERGY = e0 + λ · e1`) → `AtomwiseReduce` → wrapped in `ForceStressOutput` for autograd-conservative forces.

For all bisect runs:
- M0: `l_max=2, parity=True, num_layers=2, num_scalar_features=32, num_tensor_features=16, num_bessels=8, scalar_embed_dim=128`
- M1: `num_layers=1, num_scalar_features=128, num_tensor_features=16` (must match M0; v1 constraint)
- Gate: `EdgeFeaturesToNodeLambda` with depth-2 width-64 silu MLP, sigmoid activation, `initial_lambda_mean=0.01`
- Sparsity coeff: 1.0 (equal weight to E+F at 1.0 each)
- Optimiser: Adam, `lr=5e-4`, `grad_clip=0.3`
- Batch size: 4
- Total params: 113 K (all trainable, joint mode)

### 1.2 Stack

- torch 2.11.0+cu128 (PyTorch CUDA 12.8 wheel)
- cuequivariance 0.10.0 + cuequivariance-torch 0.10.0
- nequip 0.17.1, allegro 0.8.2 (with two local patches under `software/sparse-delta-core/patches/`: `allegro_expose_pre_final_tp_out` and `allegro_contracter_strict_false`)
- Lightning 2.x via nequip's `NequIPLightningModule`
- GPU: NVIDIA A100-SXM4-40GB MIG 3g.20GB slice on FASRC `gpu_test` partition (smoke runs) or full A100-80GB on `kozinsky_gpu` (production)

### 1.3 Dataset

`data/optb88/cameron_plus_bulkpt/split_{train,val,test}.xyz` — cameron CO/Pt slab dataset extended with bulk-Pt frames. 2196 / 274 / 276 frames, species `{C, O, Pt}`. Mean num_neighbours per type: C=12.9, O=10.7, Pt=25.2.

### 1.4 PT2 compile path in nequip

`nequip.nn.compile.CompileGraphModel` wraps the `GraphModel`. On first forward, it traces the model via `make_fx` keyed on the input-field signature, then compiles the resulting graph with Inductor (`torch._inductor.compile_fx`). Subsequent forwards with the same signature reuse the cached compiled function. The **backward** of the compiled function is generated by Inductor's AOT autograd machinery, materialising as `CompiledFunctionBackward` at the autograd-engine level.

For inputs/outputs with `requires_grad=True` (positions, model parameters), Lightning's training step does `loss.backward()`, which dispatches the autograd engine through `CompiledFunctionBackward.apply(grad_loss)`, returning gradients in input-position order: data inputs first (positions has a grad; integer fields like edge_index return None), then state-dict parameters.

For the warm-start composite with `do_derivatives=True`, `ForceStressOutput` calls `autograd.grad(E_total, positions, create_graph=True)` inside the forward to obtain forces. The result is the `forces` field that the loss reads. So during training:

1. **First backward** (inside ForceStressOutput, during forward): `autograd.grad(E, positions, create_graph=True)` to materialise forces, with `create_graph=True` so the backward through forces is differentiable.
2. **Second backward** (Lightning's `loss.backward()`): backprop through `loss = E_MSE + F_MSE + α·mean(λ)`, which depends on both `E_total` and the forces produced in step 1. This requires the autograd graph from step 1 to be intact.

When compiled, both backward passes happen inside the captured PT2 graph. This is the "double-backward" subgraph that turned out to be the failure site.

## 3. Bisect: round 1 — isolate the acceleration component

### 3.1 Hypothesis

The two accelerations stacked under production were `compile_mode: compile` and the `enable_CuEquivarianceContracter` model modifier. Either or both could be at fault.

### 3.2 Method

Three runs, each varying exactly one knob vs the broken production config. Same model, same data, same seed (217), same optimiser hparams.

| Run | compile_mode | cuEquivariance | max_epochs |
|---|---|---|---|
| `_diag` | eager | OFF | 30 |
| `_diag_b1` | eager | ON | 30 |
| `_diag_b2` | compile | OFF | 30 |

All three on `gpu_test`, A100 MIG 3g.20GB, with `Trainer(detect_anomaly=True)` plus a custom `NaNBatchLogger` Lightning callback that scans the loss and every parameter gradient each train step and dumps the offending batch to `nan_batch.pt` on first NaN.

### 3.3 Results

| Run | Job | WandB | Outcome |
|---|---|---|---|
| `_diag` | 13673587 | `8xtfq0f3` | 30 epochs CLEAN. val_weighted_sum 0.20→0.075 (best epoch 21). |
| `_diag_b1` | 13687384 | `8mjd3yhz` | 30 epochs CLEAN. val_weighted_sum 0.13→0.075. |
| `_diag_b2` | 13687385 | — | FAILED @ 9:27 with `RuntimeError: Function 'CompiledFunctionBackward' returned nan values in its 8th output.` |

### 3.4 Conclusion

cuEquivariance is innocent (`_diag_b1` is clean and uses the cueq modifier identically to v1/v2). PT2 compile reproduces the NaN on its own (`_diag_b2` NaN'd identically to v1/v2 without any cueq involvement).

**Production config locked to `compile_mode: eager` + cuEquivariance modifier** (committed `359a696`).

### 3.5 Bonus diagnostic: late-training gate collapse

The diag runs also surfaced a second, unrelated training-stability issue: late in `_diag` (epoch ~22 onwards), `λ_mean` drifts from the target sparse band (0.147) down toward 0 (0.0025 by epoch 29). With `sparsity_coeff=1.0` equal-weighted against E+F, the sparsity penalty's contribution to the loss dominates once E+F converge enough, pushing λ to zero. The other failure mode predicted by `notes/sparse_local_correction.md` §9 ("Gate → 0 everywhere"). Best val_weighted_sum still occurs at epoch ~21 with λ ≈ 0.147; standard "best-ckpt-on-val" selection catches the sweet spot automatically. Future runs may want a sparsity-coeff annealing schedule, but not blocking for this study.

## 4. Bisect: round 2 — isolate the PT2 component

### 4.1 Hypotheses (in order of plausibility for a warm-start-specific bug)

1. **Aliasing.** M1's `tensor_features_in_field` is aliased to the dict tensor M0 writes (`_allegro_pre_final_tp_out`). PT2 might mis-track this alias under graph capture + activation recompute. Test: insert an explicit `.clone()` between M0 and M1, point M1 at the cloned key.
2. **CUDA-graph capture / RNG nondeterminism.** Inductor by default uses CUDA-graph capture and seeded-Triton RNG for fallbacks. If a captured kernel sequence has subtle nondeterminism step-to-step, the recorded backward could replay a NaN-producing path. Test: disable cudagraphs, force fallback random to eager RNG, single-thread codegen.
3. **Force-backward.** `ForceStressOutput` does `autograd.grad(E, positions, create_graph=True)` inside the forward, plus `loss.backward()` from outside. Combined under PT2 compile = double-backward in one captured graph. Test: drop the force term from the loss + `do_derivatives=false`, leaving only energy gradients flowing.
4. **(deferred for budget)** Inspect the captured graph to identify which specific op produces NaN.

### 4.2 Method

B2 as the failing baseline. Each Cn changes exactly one knob.

| Run | Δ vs B2 | Implementation |
|---|---|---|
| `_diag_c1` | `clone_warmstart_tensor: true` | New `CloneField` GraphModuleMixin (in sparse-delta-core); flag inserts it between gate and M1, retargets M1's `tensor_features_in_field` to the cloned key. |
| `_diag_c2` | Inductor env vars | `TORCHINDUCTOR_CUDAGRAPHS=0`, `TORCHINDUCTOR_FALLBACK_RANDOM=1`, `TORCHINDUCTOR_COMPILE_THREADS=1` in `train.sh`. |
| `_diag_c3` | `do_derivatives: false` + `EnergyOnlyLoss` | No force computation in forward; loss has only the per-atom energy term + sparsity penalty; backward graph contains no double-autograd. |

### 4.3 Results

| Run | Job | Wandb | Outcome |
|---|---|---|---|
| `_diag_c1` | 13722662 | — | FAILED @ 9:13 with identical NaN error. |
| `_diag_c2` | 13722663 | — | FAILED @ 9:15 with identical NaN error. |
| `_diag_c3` | 13737903 | `k6zdrqm6` | **30 epochs CLEAN** in 11:38 wall time. |

C1 and C2 NaN at essentially the same wall-clock point as B2 (~9 min into the run). C3 trains 30 epochs without incident.

### 4.4 C5 offline finding (param ordering)

A separate non-GPU instrument enumerated the order of `named_parameters()` of the production composite. The first 8 parameter slots are:

```
0  m0_radial_chemical_embed.type_embed.center_embed.weight
1  m0_radial_chemical_embed.type_embed.neighbor_embed.weight
2  m0_radial_chemical_embed.type_embed.basis_linear.mlp.0.weight
3  m0_scalar_embed_mlp.mlp_module.mlp.0.weight
4  m0_scalar_embed_mlp.mlp_module.mlp.2.weight
5  m0_tensor_embed.env_embed_linear.mlp.0.weight
6  m0_allegro.first_layer_env_embed_projection.mlp.0.weight
7  m0_allegro.latents.0.mlp.0.weight
```

In nequip's `CompileGraphModel`, the captured forward function takes its inputs as `(data_inputs..., parameters...)` and the backward returns gradients in the same order. With ~7 data inputs (positions, edge_index, atom_types, edge_cell_shift, cell, batch, num_nodes), the **"8th output" of CompiledFunctionBackward corresponds to the first parameter's gradient slot** — `m0_radial_chemical_embed.type_embed.center_embed.weight`, M0's atom-type embedding. This is the earliest weight in the forward chain, i.e. the *last* one to receive gradient during backward. The NaN being detected on this slot means the upstream gradient stream already contains NaN by the time it arrives here; the actual NaN-producing op is further downstream in forward terms (i.e. closer to the loss).

### 4.5 Conclusion

PT2's force-backward graph is the failure site. The other three suspected causes are independently ruled out:

- **Aliasing ruled out.** `.clone()` of the aliased dict tensor between M0 and M1 (C1) leaves the NaN unchanged at 9:13. PT2 captures the cloned tensor as a fresh storage in the graph; if aliasing were the bug, the clone would have fixed it.
- **Inductor codegen nondeterminism ruled out.** Disabling CUDA-graph capture, eager-RNG fallback, and multi-thread compile-threads (C2) leaves the NaN unchanged at 9:15. The bug is not in the runtime kernel replay or the compile-time scheduling.
- **Force-backward subgraph is the cause.** With `do_derivatives=false` and an energy-only loss (C3), the same composite under the same `compile_mode: compile` trains cleanly for 30 epochs. The only difference vs B2 is that the captured backward graph no longer contains the `autograd.grad(E, positions, create_graph=True)` double-autograd block.

## 5. Why force-backward?

`ForceStressOutput.forward` does (paraphrased):

```python
positions = data["pos"].requires_grad_(True)
data = self.func(data)  # energy net forward
E_total = data["total_energy"]
forces = -autograd.grad(E_total.sum(), positions, create_graph=True)[0]
data["forces"] = forces
return data
```

`create_graph=True` is required so that the loss (which uses `forces` in its MSE term) is differentiable w.r.t. model parameters — i.e. the second backward through forces produces second-order grads on the parameters. Conservative forces require this single-graph structure.

Under PT2 graph capture, this becomes a backward subgraph that is itself materialised inside the compiled forward. The downstream `loss.backward()` then traverses TWO nested autograd levels — both captured in `CompiledFunctionBackward`.

The PT2 / Inductor stack handles `autograd.grad(create_graph=True)` inside a `torch.compile` region via AOT autograd's joint-graph machinery. Empirically, this composition with the warm-start composite is fragile: the joint graph contains an op (somewhere in the M1 → gate → M0 chain) whose backward implementation, when fused or recomputed under PT2's scheduling, returns NaN under specific numerical conditions reached around epoch 8–15 of joint-from-scratch training. The exact op was not pinned down — doing so would require a TORCH_COMPILE_DEBUG dump of the captured graph and a fine-grained trace, which is out of scope for the science budget (~1–2 day additional task). C5 narrows the location to "somewhere downstream of M0's first parameter in the forward chain", i.e. anywhere in M0's L>0 path, the gate, M1, the compose node, or `ForceStressOutput`'s inner grad — but the C3 result tells us that without the force-backward block, the same upstream chain works fine, so the trigger is the force-backward block specifically.

## 6. Practical implications

### 6.1 Training (current science target)

`compile_mode: eager` + `enable_CuEquivarianceContracter` is the supported production path. Stability verified for 30 epochs joint training on cameron_plus_bulkpt; `B1` run reached val_weighted_sum 0.075 at epoch 27.

Per-epoch wall time on A100 MIG 20GB: ~20-22s steady (post compile warm-up). Full 200-epoch medium-validation budget fits in ~1.5h on a non-MIG A100.

### 6.2 Inference (LAMMPS / production MD)

`nequip-compile --mode aotinductor` is a separate codepath: it compiles a **forward-only** graph for inference (positions don't require_grad at inference time; forces are computed in a single eager backward pass after the compiled forward returns the energy). The double-backward pattern that fails during training does not appear at inference. **Likely unaffected by this bug** but should be verified empirically when packaging the trained model for LAMMPS.

The local patch `allegro_contracter_strict_false.patch` (committed in sparse-delta-core `9e10612`) is required regardless of training mode, because it fixes a separate upstream bug in `Contracter.enable_{Triton,CuEquivariance}Contracter`'s `load_state_dict(strict=True)` call.

## 9. Lessons / process notes

- **`detect_anomaly=True` is the right default for a NaN hunt** — without it, the failure mode is silent loss=NaN, and Lightning's downstream `EarlyStopping(check_finite=True)` just ends the run with no traceback. With it on, the autograd engine raises `RuntimeError` with the producing `Function` name (`CompiledFunctionBackward`) and the output index, which together pin down a lot.
- **A NaN that fires on parameter slot 0** doesn't mean parameter 0 is the source. Autograd accumulates backward in reverse-forward order; the anomaly raises when the *first* NaN-contaminated grad lands on *any* leaf. For an end-to-end composite, that's usually the earliest layer.
- **Bisect by knob-flip** (one variable at a time vs a known-failing baseline) was the right strategy here. Three single-variable Cn runs on `gpu_test` (≤ 15 min each in compile mode) ruled out two hypotheses and confirmed the third unambiguously. Each variant required only a config edit (C2, C3) or a small library addition (C1's `CloneField`). Total wall-clock for the bisect including iteration on hydra config errors: ~3 hours.
- **`gpu_test` (12h cap, MIG 20GB) is the right scratch partition for these experiments.** Lab queue (`kozinsky_gpu`) has been stuck behind a multi-day maintenance reservation, but `gpu_test` schedules essentially instantly because most jobs there are short. Worth using as the default for any bisect / smoke iteration.
- **Per-run config diffs commit-able and traceable.** Each `_diag_*/` subdir captures its full state in version control, so a future reader can replay any specific run without reconstructing knobs from memory. The cost is ~50 KB of redundant YAML; the value is a permanent breadcrumb trail.
